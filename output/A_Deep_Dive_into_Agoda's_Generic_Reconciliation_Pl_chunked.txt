Reconciliation Ideology The core of reconciliation is identifying a ‘key’ and a
corresponding ‘value.’ The ‘key’ determines if two entities are comparable.
==================================================
Chunk 37:
In partner
reconciliation, for instance, thepartner_idfrom both Agoda and the partner must align for
any comparison to proceed.
==================================================
Chunk 38:
If the ‘keys’ of corresponding transactions match, we then
specify the ‘value’ to be compared.
==================================================
Chunk 39:
In the case of partner reconciliation, the ‘value’ is
a field termedpartner_amount, which represents the amount payable to the partner.
==================================================
Chunk 40:
Only
after comparison can the data be confirmed and moved to the reconciled bucket.

Generic Reconciliation The functionality of the Generic Reconciliation Platform can be
broken down into three major components.

First is the ‘Data Preparation’ phase.

In this

Chunk 81:
CI/CD Pipeline We utilize three types of tests in
the CI/CD pipeline, namely the unit test, integration test, and shadow test.
==================================================
Chunk 82:
The purpose
and functions of these tests are as follows: 1.Unit Test:This aims to examine individual
processors and services, ensuring their independent operability.
==================================================
Chunk 83:
2.Integration Test:It
focuses on evaluating the comprehensive reconciliation process and validating the outcomes
from the output tables.
==================================================
Chunk 84:
3.Shadow Test:This method involves operating modified code, for
example, Merge Request (MR) changes, on the production data.
==================================================
Chunk 85:
The goal is to compare
outcomes and assure both accuracy and validity.
==================================================
Chunk 86:
There are three steps in running the
shadow tests.
==================================================
Chunk 87:
Setup Context:This focuses on setting up the context such as branch
information and process data for shadow test.
==================================================
Chunk 88:
Run Recon:This focuses on running the
reconciliation using production data with the modified logic.
==================================================
Chunk 89:
Compare Result:This involves
updating the notes in GitLab by sharing a comparative analysis between the production
data/schema and the test result data.
==================================================
Chunk 90:
Some important aspects of shadow testing are: Shadow
tests are triggered manually.
==================================================
Chunk 91:
This is because we want to ensure that the pull request is
ready before the shadow test is triggered since running the shadow test is quite expensive
since it involves production data.
==================================================
Chunk 92:
The shadow test outcomes aren’t a mandatory requirement
for merging the PR.
==================================================
Chunk 93:
For instance, if a logical update is made, it’s perfectly normal to
expect variations in the output data compared to the production data.
